# Linux: сохранение TCP при сбоях внешней сети

Самостоятельный Docker-стенд и обязательная регрессия `linux-connection-chaos`
в `Sing-box routing checks`. Проверяет routed AWG/WG из текущих исходников,
а не случайное восстановление доступности после нового TCP connect.

## Запуск

Нужны Linux x86_64, Docker Engine с правами запуска privileged-контейнеров,
`/dev/net/tun`, поддержка network namespaces, nftables, conntrack и netem ядром.
Если возможностей нет, тест завершится ошибкой, а не выдаст PASS со SKIP.
Ничего устанавливать в систему и отключать текущий VPN не нужно.

Из checkout или распакованного исходного пакета:

```bash
bash scripts/routing/chaos/run.sh --build --suite smoke
```

`--build` нужен при первой сборке и после изменения исходников. Зависимости
загружаются только при сборке образа. Прогон запускается без внешней сети.
Для готового офлайн-образа из пакета сначала выполните `docker load -i IMAGE.tar.gz`,
затем запускайте `./run.sh --suite smoke` из распакованного пакета без `--build`.
Если доступ к Docker требует sudo, добавьте `sudo` перед командой запуска.

Обычная проверка: 20 комбинаций, AWG/WG, IPv4 внутри туннеля, bulk-download
и одновременно небольшой интерактивный WSS поток. Обрыв длится 3 секунды.
Ориентир длительности — несколько минут; зависит от ядра и машины.

Расширенная проверка:

```bash
bash scripts/routing/chaos/run.sh --suite full
```

232 комбинации: AWG/WG × внутренние IPv4/IPv6 × download/upload × 29 сценариев.
Обычный сбой длится 8 секунд; специальные blackhole — 1, 10 и 30 секунд.
Ориентир длительности — 30–60 минут. Это не тест предельной скорости.
Внешний транспорт в этой топологии — IPv4 UDP для обоих внутренних семейств.

Длительные обрывы и повторения:

```bash
bash scripts/routing/chaos/run.sh --suite soak --seconds 120
bash scripts/routing/chaos/run.sh --suite full --repeat 5
```

Для отладки одной проблемы:

```bash
bash scripts/routing/chaos/run.sh --profiles nat-rebind --protocols wireguard --repeat 10
bash scripts/routing/chaos/run.sh --profiles blackhole-30s --families IPv6 --directions upload
bash scripts/routing/chaos/run.sh --profiles idle-blackhole --seconds 30
bash scripts/routing/chaos/run.sh --list
```

В `idle-blackhole` простаивает только WSS-соединение; bulk остаётся активным.
`--seconds` меняет длительность обычных сценариев. Именованные `blackhole-1s`,
`blackhole-10s`, `blackhole-30s` сохраняют указанную в имени длительность.
`--recovery-seconds N` задаёт явный предел ожидания прогресса: по умолчанию 30 с,
в soak — 150 с. Увеличение этого предела меняет критерий приёмки и отражается
в отчёте; оно не ускоряет VPN и не меняет таймеры TCP.

## Что моделируется

| Сценарии | Воздействие на внешний путь |
|---|---|
| `blackhole`, `uplink-blackhole`, `downlink-blackhole` | Полная / односторонняя потеря зашифрованного UDP, без смены интерфейса |
| `blackhole-1s`, `blackhole-10s`, `blackhole-30s` | Короткие и длинные молчаливые обрывы |
| `idle-blackhole` | Простой WSS во время обрыва, затем использование того же сокета |
| `loss`, `burst-loss` | Случайные и коррелированные потери |
| `uplink-loss`, `downlink-loss` | Несимметричные потери |
| `delay`, `reorder`, `duplicate`, `corrupt` | Задержка/джиттер, изменение порядка, дублирование, повреждение пакетов |
| `rate`, `queue-overflow`, `mixed` | Узкий канал, переполнение очереди, сочетание нескольких дефектов |
| `link-down`, `flap` | Выключение интерфейса и серия четырёх переключений |
| `address-gap`, `address-move` | Временная потеря адреса / переход на другой адрес |
| `route-blackhole`, `default-removal` | Чёрная дыра маршрута / отсутствие default при сохранном маршруте до peer |
| `nat-rebind` | Реальный SNAT на другой внешний IPv4-адрес и UDP-порт с удалением старого conntrack-состояния |
| `mtu`, `mtu-blackhole` | Снижение MTU локального интерфейса / молчаливая потеря внешних UDP-пакетов размером >900 байт при сохранении маленьких handshake |
| `handover` | Удаление старого veth, новый интерфейс, gateway и префикс при той же идентичности peer |
| `domain-move` | Старый endpoint недоступен, DNS имени сервера указывает на другой адрес того же peer |

Распределения и проценты находятся в `fault.py`, не скрыты в контейнере.
Netem стохастический: одинаковые параметры не гарантируют одинаковый набор
потерянных пакетов. Для воспроизведения сохраняйте kernel version, параметры
и отчёт; для проверки устойчивости используйте повторения.

## Как отличаем сохранение TCP от переподключения

1. Стенд поднимает реальный TUN и штатный `amnezia-routing` без диагностических
   изменений TCP-зависимости. На другой стороне AWG/WG находится настоящий
   Linux TCP-стек в отдельном namespace.
2. Один раз открываются WSS и длительный TLS bulk-поток. Данные имеют номера
   последовательности и проверяемое содержимое. У потоков нет reconnect/redial.
3. После начала передачи вносится сбой исключительно во внешний путь.
   Для blackhole проверяются счётчики реально потерянного UDP, для netem —
   обработанные пакеты, для NAT — создание нового SNAT соответствия.
4. После снятия сбоя те же потоки должны передать минимум три новых сообщения
   WSS и три полные bulk-записи. Сервер по-прежнему должен иметь ровно два
   исходных TCP accept, по одному на каждый поток.
5. Для fault-сценариев дополнительно проверяются тот же PID/starttime helper
   и тот же ifindex TUN. Миграции используют существующие проверки штатного
   автоматического восстановления пути без тестовой команды refresh.
6. В конце намеренно закрывается runtime: старые потоки обязаны разрушиться,
   а новый WSS получает другой session ID. Это контроль чувствительности теста.

Возобновление может задерживаться из-за RTO TCP, особенно после длинного обрыва.
`resume_ms` — время до подтверждённого прогресса обоих потоков после снятия
инъекции, а не ping, не время handshake и не обязательно время первого байта.
Бюджет — предел ошибки теста, а не обещанная скорость восстановления.

## Результаты

По умолчанию: `./chaos-results/<UTC-время>/`.
Можно выбрать каталог: `CHAOS_OUTPUT=/абсолютный/путь bash scripts/routing/chaos/run.sh ...`.

- `report.json`: результаты каждой комбинации и измерения восстановления;
- `junit.xml`: обычный отчёт для CI;
- `environment.json`: ядро и параметры запуска;
- каталог каждого сценария: полный `run.log`, nft/tc/conntrack evidence,
  текстовая TCP-трасса синтетического peer и `ss` с состоянием TCP/таймеров.

Ошибка любого сценария даёт ненулевой код завершения. Остальные сценарии
продолжаются, чтобы собрать всю картину. Уже выполненные результаты сохраняются
после каждой комбинации; незавершённый прогон имеет статус RUNNING, а не PASS. Изолированный namespace удаляется по окончании процесса.

## Регрессии приложения и границы стенда

`Sing-box routing checks` включает smoke как обязательный job в общем gate.
Полная матрица и soak доступны отдельным workflow `Linux extended TCP chaos`.
Существующая проверка установленного Linux-пакета дополнительно вносит полный
UDP blackhole и выключение физического veth по 3 с: реальный WireguardProtocol
→ Qt service → helper, AWG/WG, strict kill switch включён/выключен. Проверяются
неизменные runtime UUID/PID/TUN, echo/bulk сокеты и состояние протокола Connected.

Образ этого самостоятельного пакета проверяет native core/TUN, не GUI,
не установщик и не systemd-resolved. Полная цепочка проверяется отдельным
обычным installed-service тестом. Никакой тест здесь не использует ваши серверы,
профили или учётные данные.

Контейнер не воспроизводит физический Wi-Fi/модем, ошибки драйвера/прошивки,
настоящий suspend/resume машины, captive portal и DPI конкретного провайдера,
внешний IPv6/NAT64. Он моделирует их отдельные сетевые последствия. IPv6 внутри
туннеля не является проверкой IPv6 внешней сети. Смена сервера с утратой его
TCP-состояния и прикладной таймаут, истёкший до возврата сети, не могут дать
сохранение старого end-to-end TCP средствами одного клиента VPN.

Для финальной ручной проверки на отдельной Linux-машине:

1. Подключиться через routed AWG/WG к своему тестовому серверу.
2. Открыть одно длительное TCP-соединение без автоматических повторных connect
   (свой echo-клиент/WebSocket с отключённым reconnect) и длительную передачу.
3. Отключить Wi-Fi на 3/10/30 с, затем отдельно проверить Wi-Fi → Ethernet,
   уход/возврат из сна и смену Wi-Fi сети.
4. На клиенте и сервере сравнить тот же TCP 4-tuple/session ID, отсутствие нового
   SYN/accept, последовательность и целостность данных. Сохранить время последнего
   подтверждённого сообщения, возврата сети и первого сообщения после него.
   Один успешный ping, новая загрузка страницы или `curl --retry` этого не доказывают.
5. Отдельно повторить с kill switch и split tunneling; сравнить журналы службы
   и helper, отсутствие пересоздания runtime/TUN. Собирать сетевую трассу только
   на своей тестовой машине, учитывая возможные данные других приложений.
